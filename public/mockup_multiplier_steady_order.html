📐 Simulasi Urutan Baris Kampanye Multiplier Steady Ascending (1..N)

Memastikan baris kampanye dari Baris #1 hingga Baris #N selalu berurutan permanen seperti pada Kampanye Pilar.

❌ Perilaku Sebelum (Unsorted / Jittery)

Database mengeksekusi ORDER BY t.created_at DESC tanpa tie-breaker. Saat status salah satu baris diupdate oleh worker, baris tersebut melompat posisi di heap PostgreSQL. Setiap polling 5 detik, urutan baris tertukar secara acak.

✅ Perilaku Sesudah (3-Layer Steady Ascending)

Urutan dikunci permanen: Database ORDER BY t.row_index ASC, t.id ASC, API melakukan numeric sort, dan Frontend mempertahankan posisi Baris 1 s/d N. Baris tidak akan pernah bergeser meskipun status fase terus berprogres.

Mode Tampilan:
# Angle & Judul Konten (Berdasarkan Sudut Pandang) Fase Eksekusi Status Baris

🏛️ 3-Layer Steady Ordering Architecture

LAPIS 1 (DB)
Query Khusus Batch di lib/db.js: Fungsi getMultiplierTasksByBatchId(batchId) mengunci urutan dengan ORDER BY t.row_index ASC, t.id ASC (sama seperti listPillarCampaignItems pada Kampanye Pilar).
LAPIS 2 (API)
Deterministic Sort di app/api/v2/multiplier/route.js: Endpoint GET ?batchId=... melakukan numeric sorting ascending pada row_index dan task.id sebelum mengembalikan JSON.
LAPIS 3 (UI)
Stable Sequence di app/multiplier-lab/[id]/page.js: State tasks mengurutkan data saat di-fetch dan kolom nomor urut mengikat nomor asli row_index + 1, menjamin Baris #1 selalu Baris #1.
